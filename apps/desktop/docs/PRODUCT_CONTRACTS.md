# Grox v0.3.2 产品契约

这份文档约束用户体验和实现边界。它不是愿望清单；改动若破坏下列不变量，必须在 PR 中明确说明原因和迁移方案。

## 核心旅程

1. 用户进入首页后可以浏览最近任务、选择媒体类型、整理输入和附件。
2. 官方 Grok Build CLI 是运行任务的硬条件：未检测到 CLI 时必须明确引导安装，不能伪造可用状态。
3. 账户是发送任务前的软门槛：首次引导可以稍后处理，输入内容不得因此丢失；发送时若仍未认证，再打开账户配置。
4. 任务开始后，对话是主工作面。文件、计划、终端、预览和并行任务共享唯一右侧工作区，同一时刻只展示一个，避免多列叠加压缩正文。
5. 用户切换任务或工作区不能打断后台 turn；恢复后必须看到真实状态，而不是由视图猜测状态。

## 会话状态不变量

- Bridge 只报告 ACP 事实；Store 只投影视图；`SessionRuntime` 是前端唯一的会话可操作性决策层。
- “是否忙碌”“能否接收主提示”“门控解决后状态”“队列是否可排空”不得在组件中重复推断。
- 连接状态与回合状态是两条事实：自动重连成功不能把被中断回合改写为成功。
- `session/prompt` RPC 的成功、失败或用户取消是回合结束的唯一裁决；`turn_completed`、`prompt_complete` 等通知不能提前触发 idle 或队列排空。
- 待审批和待回答属于发起会话的未解决门控，不能被上游的 running 信号误降级，也不能因切换到其它会话而改变路由。
- 提示队列按会话持久化。异常退出、停止和持久化失败必须暂停自动排空；只有用户显式“确认并继续”才能解除事故门禁，发送新提示不能被解释为同意重放旧队列。
- 应用 journal 负责展示连续性，Agent 历史负责模型上下文；打开会话必须对账两者，任何已有 journal 都不能阻止读取更新的 Agent 尾帧。
- journal 必须记录回合是 active 还是 settled。启动时发现 active 回合要呈现为 interrupted 并暂停队列；正常回合结束后进行有界延迟对账，新回合开始立即取消旧对账。
- 错误必须暴露真实原因；不得用静默 fallback、伪成功或默认空数据掩盖协议和持久化故障。
- 协议错误、用户操作错误和运行环境错误必须保留稳定分类，分别给出上下文与恢复动作。

## 信息架构

- 首页只保留媒介选择、主输入、必要的运行状态和最近任务；调试路径、会话 ID、ACP 连接细节不进入主视觉。
- 已安排任务运行在独立后台会话中，只在应用进程存活且所有会话空闲时触发；完全退出后不得宣称仍在后台运行。
- 自动化必须保留有界的本机运行记录，并区分启动中、已启动、跳过、错误和结果未知；“已启动”只证明提示已交给当前 Agent 运行时，不代表完成。
- 本地图片、视频、音频和 PDF 使用带随机令牌的回环地址交付；大媒体必须支持 Range 请求，不能以 Base64 整段注入 WebView。
- 侧栏只有“显示”和“隐藏”两种确定状态；隐藏后不保留不可见热区，恢复入口由标题栏和快捷键提供。
- 设置按“个人”和“扩展”分组，所有高频设置必须可搜索；每个分区提供稳定的 `#/settings/<section>` 深链。
- 危险操作使用应用内确认框，并写清影响对象、不可逆后果和失败原因。
- 环境摘要必须显示应用 journal 的数量、体积、待迁移和不可读状态，使持久化健康可被用户和支持人员检查。

## 排版与交互

- 普通界面正文默认不低于 12px；9–10px 只用于非必要的短元数据。
- 中文界面不滥用全大写、超宽字距和工程术语。术语不能替代用户结果，例如“开始任务”优先于“建立 ACP 链路”。
- 动效只表达进入、状态变化和层级关系；不得用弹跳、持续缩放或边缘自动展开改变控件命中区域。
- 暗色与亮色主题必须保持相同的信息层级、可读性和焦点状态。

## 社区反馈与发布完整性

- Bug 报告必须包含平台、Grox/CLI 版本、复现步骤、预期和实际结果；日志模板提醒用户删除敏感信息。
- 功能建议先描述问题和期望结果，再讨论实现。社区来源统一使用 `from:community` 标签。
- v0.3.2 正式发布至少包含 Windows x64 安装包与便携包、macOS Apple Silicon/Intel DMG、Linux x64 AppImage/deb/rpm，以及 `SHA256SUMS`。
- 版本号必须在 `package.json`、`Cargo.toml`、`Cargo.lock` 和 `tauri.conf.json` 中一致；发布说明必须列出已知限制和各平台资产。
