# ADR 0005：供应商密钥由 Host SecretStore 单点持有

- 状态：已采纳
- 版本：v0.3.2
- 日期：2026-08-15

## 背景

旧实现把同一把兼容服务密钥同时写入 `~/.grok/grox-providers.json` 与受管 `.env`，运行时再从 `.env` 读回。WebView 虽然拿不到正文，但原生层存在两份可变事实源：档案更新、供应商切换或写入中断都可能留下旧密钥；“已安全保存”的界面文案也没有说明真实存储位置。

关键问题不是把 JSON 权限改成 0600，而是密钥正文、密钥存在性、活动供应商和运行时注入缺少唯一权威。

## 决策

新增 Host `SecretStore`，并建立以下不变量：

- 密钥正文优先写入 macOS Keychain、Windows Credential Manager 或 Linux Secret Service；平台凭据库明确不可用时，显式降级到 `~/.grok/grox-secrets.json`，原子写入并限制为 0600；
- `grox-providers.json` 永不序列化 `apiKey`；受管 `.env` 只保存供应商类型、端点、模型目录和非敏感档案引用；
- 真实密钥只在启动选定的 Grok Build 子进程时解析并注入 `XAI_API_KEY`，不会回传 WebView、写入诊断或进入普通配置投影；
- 旧档案和旧受管 `.env` 采用惰性迁移：先成功写入 SecretStore，再删除旧明文。后续元数据写入失败时保留旧副本，避免凭据丢失；
- 活动兼容档案由受管环境中的档案引用与端点共同确认，不再以 `ProviderProfilesFile.activeId` 作为第二个运行时事实源；引用缺失或端点不一致时显式失败，禁止回退到另一把直连密钥；
- 删除先让密钥引用对 Grox 不可读取。若 OS 凭据库暂时无法清理旧项，私有元数据写入墓碑，防止凭据库恢复后旧值复活；下一次显式保存该引用时清除墓碑；
- WebView 只能看到 `keychain`、`private_file`、`legacy_file`、`missing` 四种后端状态。私有文件降级不是“安全保存”的模糊成功，而是用户可见的较弱存储级别；
- 不在启动或设置页渲染时探测、解锁凭据库。只有迁移、保存、运行或其他明确需要密钥正文的动作才访问 OS 凭据库。

供应商命令同时改用共享 `HostError`，在原生边界区分用户操作、上游协议和本机环境错误；模型目录的无效 JSON/HTTP 响应不再与凭据库或网络失败混为同一个字符串。

## 结果

供应商密钥现在只有一个持久化边界，档案编辑、激活、刷新模型、直接配置、删除和 ACP/媒体运行时注入都经由同一 SecretStore。界面展示实际存储后端，结构化错误保留稳定 code 与恢复建议。

受限文件后备仍弱于 OS 凭据库，这是有意且可见的兼容策略；完全禁用后备会让没有可用 Secret Service 的 Linux 环境无法使用 API 服务。后续支持包只能导出后端类型、引用数量和迁移状态，不能导出引用对应的正文。
