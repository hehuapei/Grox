# ADR-0002：应用 journal 与 Agent 历史分别承担展示连续性和模型上下文

- 状态：Accepted
- 日期：2026-08-13

## Context

Grox 原先把应用侧记录当作可丢失的 UI 缓存：只保留少量截断块，读取或写入失败会被吞掉，并且打开会话时只要缓存存在就不再读取 Agent 磁盘历史。结果是 Agent 已经落盘的最终回复可能被较旧缓存遮住；异常退出后，应用也无法区分“回合已完成”和“只保存到流式中途”。

Agent 的 `chat_history.jsonl` 是模型上下文来源，但不包含 Grox 的全部展示状态、提示队列和本地交互事实。把任一来源宣称为唯一记录都会丢失另一侧信息。

## Decision

1. 每个应用会话持有版本化的应用 journal，记录应用会话 ID、Agent 会话 ID、保存时间、回合状态和有界展示快照。
2. 应用 journal 是界面连续性的权威来源；Agent 历史是模型上下文和执行证据的权威来源。打开会话时始终读取并合并两者，较旧 journal 不能遮住 Agent 已落盘的尾部回复。磁盘预览按 `assistant.tool_calls` 与后续 `tool_result` 的真实调用 ID 恢复公开工具事件；没有结果的调用标为取消，不能推断成功。内部 reasoning 不进入该预览；有界预览发生截断时必须显示说明，不能悄悄伪装成完整历史。
3. 正常回合结束后进行有限次数的延迟对账；新回合开始会使旧对账失效，避免旧尾帧覆盖新状态。
4. 启动时若最近 journal 仍为 active，先查询 Host 活动回合：Host 回合仍在时恢复 running/streaming 状态并继续补放；Host 回合已经消失时才呈现为 interrupted 并暂停提示队列。恢复连接不能将未知结果推断为成功。
5. journal 损坏、身份不匹配或写入失败是可见的环境错误，不再等价为“没有缓存”。旧版裸会话缓存只在首次读取时兼容，并在成功写入新版 journal 后迁移。
6. v0.3.2 暂时让应用会话 ID 与 Agent 会话 ID 取相同值，但在 journal 中分别记录，保留未来解除一对一绑定的迁移边界。
7. 工具图片不以内联 Base64 写入 journal。Host 将经过内容类型、单图 8 MB 和单次 16 MB 校验的图片按 SHA-256 保存到 `sessions/<id>/media`，journal 只记录受控文件引用；恢复会话时仅授权该会话的 media 目录。
8. journal、工具图片和会话删除共用原生存储门禁。删除先写入进程内 tombstone 并持锁清理整个会话目录；已进入异步队列的晚到写入必须失败，不能重新创建被删除的会话。
9. ACP 会话事件按 session + stream + 精确 sequence 记录在待写 journal 中；只有 Host 校验并原子写入该快照后才确认对应事件。全局“已看过”游标不能替代耐久确认，工具图片事件必须等到 Base64 被受控文件引用替换后再确认。

## Consequences

- 崩溃恢复不会自动重放可能已经执行过的提示，用户需要检查末尾内容后显式恢复队列。
- 长会话保留更多展示记录并使用 16 MB 上限，磁盘占用高于旧缓存；环境摘要会显示数量、体积、待迁移与不可读条目。
- 对账只补充可验证的磁盘事实，不恢复流式副作用，也不把 active 快照猜成完整结果。
- 进程池或后台会话并发必须建立在此 journal 不变量之上，不能另建第二套恢复状态机。
- 工具截图可在重启后恢复，并随会话永久删除；图片落盘失败会作为环境错误呈现并保留事件以供补放，而不是静默丢失或提前确认。
